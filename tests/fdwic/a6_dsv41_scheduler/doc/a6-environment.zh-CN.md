## 三处判断边界

- **编号超过 53 不能证明 `0x0FFF` 掩码错误。** 已列出的编号都在该掩码范围内；尚未解清的是编号如何对应 C/V、die 和 `res_id`。
- **单 block 的 `get_block_idx()=0` 正常，`get_coreid()=0` 也不能单独证明身份读取失效。** 先做多 block、分入口记录，不预先假定必须换成 AICPU 启动。
- **顶层 MIX ELF 用 `dav-920r1` 启动成功，不能直接推广到所有计算核。** HBG 计算核由运行时通过函数地址调用，与直接交给 ACL 启动的 ELF 不同。

## 未解决项：用途、验证与通过标准

### 1. 重新验证核身份

**缺什么／用途：** 可靠的 C/V 原始身份及逻辑 block 对应关系。先排除探针覆盖或误编译，才能确定核编号解码与 worker 配对；与 `res_id` 的最终关联由第 4 项补齐。

沿用成功的 MIX 启动方式，分别运行 blockDim **1、2、4**。Host 先把记录区填成明显的哨兵值；每个入口用 GM 原子计数领取独立槽，再写入：

```text
入口标记 C/V、原始 get_coreid（不加掩码）、
block_idx、block_num、subblock_id、subblock_dim、记录槽号
```

不要用待验证的 coreid／block_idx 分配槽，避免覆盖。哨兵用于区分“实际读到 0”和“没有写入”。

**通过标准：** 每次获得完整的 C/V 记录，各逻辑 block 的覆盖可核对。若多 block 的 AIC 仍全部为零，在回答区贴两个入口的关键预处理／反汇编片段及写回代码，先确认没有误编译或记录覆盖，再判断身份寄存器。

### 2. 确定 SSBUF 调度区并验证双向握手

**缺什么／用途：** 调度状态可以放在哪个区间，C/V 是否共享该区间，以及读写需要哪些屏障。这决定 [调度状态结构与访问函数](../../../../src/a5/runtime/host_build_graph/runtime/scheduler/scheduler_cluster_signal.h) 的 A6 改法；容量已知不等于可用位置和共享协议已知。

| 步骤 | 验证方法 |
| ---- | -------- |
| 确定可用位置 | 用目标编译宏核对 KFC 结构的 `sizeof`／`offsetof`，检查实际调用的初始化、清零代码及写入范围 |
| 验证共享与同步 | 同一对 C/V 用不同序号、不同数据往返握手；先一组，再多组同时执行 |

SDK 的 `asc/impl/basic_api/dav_9201/kfc/kfc_comm.h` 中，`ClearSSbufImpl()` 还包含显式计算偏移的写入。**不能只看 `sizeof(SsbufWorkspaceDesc)`，就认定后面的空间空闲。**

在核实可用区间后，按以下协议测试，屏障选择须有 A6 对应依据：

```text
完成初始化，并明确通知双方可以开始
C：写 payload → release 屏障 → 写 ready=序号
V：等 ready → acquire 屏障 → 校验 payload
V：写 response → release 屏障 → 写 ack=序号
C：等 ack → acquire 屏障 → 校验 response
```

**通过标准：** 连续多轮数据正确、不串轮；多组使用不同数据，不串组；记录错误数与超时数。最终使用拟放进 HBG 的实际结构和访问函数验证。单入口写 `0x2222` 再读回只能证明访问成功，不能替代 C/V 共享验证；动态 SSBUF 指针失败的对照也需保留，用于核对真实访问函数。

### 3. 验证外层 MIX 调用计算核

**缺什么／用途：** `dav-920r1-cube/vec` 的计算核产物，能否被可启动的 A6 外层按生产 ABI 调用。这个结果决定核编译／加载入口如何接入，而不是直接把所有核改成通用 MIX。

HBG 在 [resident_scheduler_impl.h](../../../../src/a5/runtime/host_build_graph/aicore/resident_scheduler_impl.h) 的 `execute_task()` 中执行：

```cpp
UnifiedKernelFunc kernel = reinterpret_cast<UnifiedKernelFunc>(function_address);
kernel(reinterpret_cast<__gm__ int64_t *>(args));
```

最小验证保持这一调用方式，不需要整套 HBG 或 SWA：

```text
可启动的 A6 MIX 外层
  ├─ C：调用单独编译、链接、提取并上传的 C 计算核
  └─ V：调用单独编译、链接、提取并上传的 V 计算核
         ↓
  子核各自写不同校验值，返回后外层再写完成标记
```

**通过标准：** 两个子核均被正确调用并返回，参数、核输出和外层完成标记均正确。失败时区分外层启动、核地址／参数、子核执行、返回四个阶段，不能用外层 ELF 启动成功代替这一项。

### 4. 接通 AICPU 探针并补齐寄存器映射

**缺什么／用途：** CP1 执行链和控制地址表，供运行时向正确的 C/V 发布启动信息、读取状态并完成退出。不能等完整 HBG 跑通后再查这些接口，否则形成循环依赖。

复用 [aicpu-device-query](../../../../tools/cann-examples/aicpu-device-query/README.md) 的上传／启动骨架，先让 AICPU 只向 GM 写校验值，独立证明 CP1 可执行。并行查找下面的接口依据：

| 缺失信息 | 用途 |
| -------- | ---- |
| 有效 `res_id` 与硬件核编号、die、C/V 配对的关系 | 将任务和握手发给正确的核，避免把可映射槽数当成计算组数 |
| 每个映射窗口内 C/V 的起点、跨度 | 从映射基址找到对应核的控制窗口 |
| `DATA_MAIN_BASE`、`COND` 及实际启动／退出所需寄存器的偏移、宽度、读写方 | 按硬件契约读写启动／状态／退出信息 |

取得适用于 A6 的资料或工作实现后，在正确的 CP1 进程中使用映射地址；让 C/V 发布不同握手值，由 AICPU 读取并建立关联，随后验证启动和退出往返。Host 不直接解引用 CP1 的 VA，也不通过猜偏移试写 MMIO。

**通过标准：** 明确对应“硬件核编号—`res_id`—C/V 窗口”，且握手完成。仅凭 70 个映射成功、每份 2 MiB 仍不能填写偏移表。找不到定义时返回具体缺项与查找范围，保留资料版本、路径和关键片段。

### 5. 验证 HBG 最小任务再接 SWA

**用途：** 前面取得的是平台接口和最小调用证据，还需验证实际调度的任务完成、依赖推进与退出。

接口适配后按以下顺序逐步验证：

```text
单个 AIV 任务 → 单个 AIC 任务 → 有依赖的 C/V 任务
             → 一组 MIX 协作任务 → 独立 SWA
```

组包前按 [使用方法](usage.zh-CN.md) 核对目标编译与 Host plan ABI；已有检查结果直接复用，不另列重复查证任务。

**通过标准：** 最小任务输出正确、依赖满足后才推进、正常退出；SWA 检查完整输出，具体口径见 [验收要求](a6-migration.zh-CN.md#验收要求)。本轮只跑单卡 HBG，不扩展 percounter。计时沿用已确认配置；AICPU 探针可顺带核对其计时源，不另做性能采集。
