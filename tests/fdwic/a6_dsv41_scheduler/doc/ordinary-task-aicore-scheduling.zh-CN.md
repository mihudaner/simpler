# 普通 Task 的 AICore 调度与 L2 泳道

普通 task 的一个 block 由一个 AIC（普通 C）或一个 AIV（普通 V）执行。L2 泳道用三个时间点描述一次派发。**领到 block** 表示这个核负责它，**READY** 表示输入已满足、槽位已发布，**executor pickup** 表示本核执行器已经选中它。前两步可以提前发生，中间的时间条可以包含等待。[普通任务调度实现][token]

标签按官方 `main@dcb6a367f` 的 HBG 转换器整理。例如新版 `t22-b10-Claim and bind` 对应 005 旧图的 `Claim and bind · t22 b10`。005、006 的数字来自 A5/A6 迁移实验，下文标明平台和轮次。图中的 **L2** 指泳道采集等级。[新版标签与端点][labels] · [005 报表][005]

## 一、每一段在做什么

| 005 报表阶段        | 新版泳道标签                                          | 从哪里到哪里，做了什么                                                                                                                                                  | 主要硬件通路                                                                                                                                                   |
| ------------------- | ----------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ① 领取或绑定       | `Claim and bind`                                    | 从开始领取，到本核绑定一个具体 block。Host 已备好函数、参数和上下文，常驻 worker 确定 block 编号，接收对应的 Call，把执行身份记到自己的普通槽位。此时前驱可以仍在运行。 | AIC/AIV 的标量单元读任务目录、GM 中的调用记录。满足整波固定归属条件时直接由核编号算出 block。动态分配时通过 GM 原子加取票，多 block 可分四个计数区以分散竞争。 |
| ② 观测前驱         | 下表三种标签                                          | 从绑定完成，到确认所有输入依赖满足。按顺序查前驱，记住已通过的位置。遇到 pending，保存前驱及其完成状态地址，稍后重查。                                                  | 先查本核保存的 DONE 结果。需要访问共享状态时，A5 按任务映射读 CntNotify 阈值或完成标志，005/006 迁移版 A6 走 GM，读取前驱自己的完成状态字。                    |
| ③ 就绪及发布       | `Predicate and READY publication`                   | 从确认依赖满足，到发布 READY。有执行条件时先求值，条件为假则标记跳过业务核，仍须走收尾。把工作留在原槽位。                                                              | 主要是本核标量判断、更新私有槽位。L2 另取设备时间戳并记录轨迹。                                                                                                |
| ④ READY 到领取     | `READY to executor pickup`                          | 槽位已经 READY，直到执行器选中该槽、核对归属并接手。首批任务可能等 AICPU 放行，运行中也可能等本核调度循环或顺序约束。                                                   | 常规接手通过核内槽位。存在更早的协同任务时可检查组内顺序状态。首批启动还涉及 AICPU 与 AICore 的寄存器握手。                                                    |
| ⑤ 入核准备         | `Kernel entry preparation`                          | 从接手到业务核入口。取已绑定的调用上下文，按需处理异步输入可见性，完成入核前的屏障和采集动作。                                                                          | 标量单元访问 GM 中的 Call 和上下文。普通路径执行 DDR 屏障。有异步输入可见性要求时，按范围执行数据缓存维护（DCCI）。                                            |
| ⑥ 业务核体         | `Worker View` 中业务核条带的 `kernel-duration-us` | 从进入函数到函数返回。例如输出量化在 V 核执行，投影乘法可在 C 核执行。查看算子本身的耗时用这一列。                                                                      | 取决于核函数，例如 AIV 的向量指令、AIC 的矩阵指令，以及算子自己的数据搬运。                                                                                    |
| ⑦ 核返回到观察完成 | `Kernel return to completion observation`           | 从业务核返回，到执行它的本核记下完成观察点。包括适用的异步注册封口、执行记录归还等。此时下游可能还没看到 DONE。                                                         | 本核标量收尾，按完成后端更新或发布 GM 执行状态。采用 GM 记账的普通路径可以在这个打点之前贡献完成数。                                                           |
| ⑧ 本地完成与释放   | `Local completion and release`                      | 从本核完成观察点，到本次执行的 L2 收尾端点。计数型路径在此发布完成贡献。端点之后代码还会写回 L2 轨迹、回收私有槽位。有异步条件时，整个逻辑任务可以稍后才 DONE。         | A5 计数型任务向 CntNotify ADD 写完成贡献，其他路径按协议更新 GM。L2 轨迹写回有自己的缓存维护开销。                                                             |

① 的“领”决定谁负责，④ 的“领”决定何时执行。④的 READY 标记保存在槽位内，由本核执行器直接读取。⑤到⑧的边界来自设备打点，尤其不能把⑦或⑧整段当成单次 CntNotify 或 GM 指令延迟。[领号与分区][claim] · [READY 发布][ready] · [执行器入核与返回][exec] · [完成打点与回收][complete]

### ② 为什么有三个英文名字

| 泳道标签                                   | 计量范围                                                                                                                                  |
| ------------------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------- |
| `Bound to first pending observation`     | 绑定完成 → 第一次查到某个前驱尚未完成。                                                                                                  |
| `Predecessor pending to inputs observed` | 第一次查到 pending → 确认**所有**输入满足。事件参数 `first_pending_predecessor` 指最先遇到的阻塞前驱，此后可能还需检查其他前驱。 |
| `Bound to predecessors observed`         | 本次没有记录到 pending，直接画出“绑定完成 → 确认所有输入满足”。                                                                        |

一个实例遇到 pending，就把前两条相加得到报表的“观测前驱”。走第三条的实例直接取该条。不同 worker 的等待可以同时发生，不能把全卡等待相加当成整图耗时。[渲染规则][labels]

## 二、三条容易混淆的硬件通路

| 要回答的问题                   | 谁和谁通信                                                                                                                                                                                                                    | 读图时的含义                                                                                                                                                                                                                                        |
| ------------------------------ | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| 整张图可以开跑了吗？           | **AICPU → AICore**。首批槽位可在 bootstrap 期间准备。迁移实验中 A5 经 `DATA_MAIN_BASE` 放行各 worker，A6 经 `IPC0`。                                                                                               | 首批普通 task 可以先 READY 再等放行，因此④可能很长。新版主仓 A5 的 bootstrap 还可通过 CntNotify 位图向 AICPU 报到，报到和最终放行是两个动作。[迁移版启动协议][launch] · [主仓启动协议][boot]                                                      |
| 前驱任务的结果可以消费了吗？   | **生产者 AICore → 共享完成状态 → 消费者 AICore**。CntNotify 是设备的硬件通知计数资源，生产者可向映射的 ADD 地址加计数，消费者从读口看是否达到阈值。GM 是设备全局内存，GM 路径用原子操作更新任务状态，消费者读状态字。 | 这条通路影响②以及⑦、⑧的部分工作。生产者仍在计算时，消费者在②看到的 pending 是真实的数据依赖等待。[完成状态选择][sources] · [CntNotify 读写][counter]                                                                                           |
| READY 后由谁把工作交给执行器？ | **同一个 AICore 内部**。常驻标量调度器选择本核私有槽位。主仓当前每核有一个普通槽和一个 MIX 成员槽。图中若有顺序约束，选择普通槽前可能查看集群共享缓冲区 SSBUF 中的进度。                                                | 等待中的普通槽保留原任务，同一核可以先推进另一槽的可执行工作。AICPU 判定整图结束另看末端任务。早期 002 的“整轮 GM 加一”和 005/006 的“某个前驱可消费”也要分别读。[本核选择与顺序约束][order] · [当前末端判定][sinks] · [002 整轮计数实验][002] |

## 四、为了缩短这些阶段，已经试过什么

下列结果各有自己的基线。L2 可以定位各阶段，L0 用于核对整图收益。以 005 A5 为例，同一配置从 L0 到 L2，核窗口从 **156.759** 增至 **168.817 µs**，Device wall 从 **245.012** 增至 **579.470 µs**。比较方案时应对齐采集等级。[005 整轮计时][005]

| 针对哪一段              | 实际尝试                                                                                                                 | 结果                                                                                                                                                                                                                                                                                              |
| ----------------------- | ------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| ① 动态取票竞争         | Host 对满足整波条件的任务预定 block 归属。动态路径保留分区取票。另一次试验让 worker 记住本任务票已领尽，避免反复原子加。 | 固定归属已进入实现。后一个试验的确定性测试中，重复原子请求 **72 → 2**。A5 十二用例 L0 均值之和反而 **+0.399%**。该策略因消除冗余请求被保留，未取得整图加速证据。[固定归属改动][fixed-change] · [取票试验][tickets-trial]                                                            |
| ② 重复查依赖           | 缓存已完成的前驱和已走过的前缀。Host 还试过把只有一个消费者的控制节点折叠进该消费者，直接检查真实生产者。                | 前缀缓存用于当前路径。控制节点折叠方案保留。十二用例 L0 总和 **−0.184%**，六快六慢。它减少中间检查，前驱业务核的执行仍在关键路径上。[前驱观察实现][sources] · [折叠实验][fold]                                                                                                            |
| ④ READY 后等顺序许可   | 试过让 Host 为普通任务生成更强的完成证明，满足条件时跳过一次 MIX 顺序检查。                                              | A5 MoE 的 t28 在 rank 0 的 READY→领取 **0.829 → 0.385 µs**，但七用例 L0 总和 **+0.528%**，方案撤回。只盯这一条容易高估收益。[顺序检查实验][floor-trial]                                                                                                                            |
| ⑦、⑧ 完成计数         | 002 对照 96 核同址 GM 普通读、GM 原子读和 CntNotify 读，并检查 A6 的计数 ADD 入口。                                      | 第 96 个读者完成时间的均值，按上述顺序，A5 为 **1.660 / 16.387 / 1.199 µs**，A6 为 **0.503 / 0.990 / 1.225 µs**。A6 的 CntNotify SET/read 验证通过，ADD 映射未通过。该实验采用 GM 完成计数。读微测和 005/006 均未给出 A6 同卡切换完成后端的整图收益。[002 同址微测与 ADD 验证][002] |
| ⑦、⑧ 返回后的本地收尾 | 试过把入核前保存的执行槽快照直接交给完成逻辑，省一次复制。                                                               | 同卡 A5 SWA 的 L0 Device 中位数 **928.160 → 928.244 µs**，完成段也没有稳定缩短，方案撤回。[执行槽快照实验][snapshot]                                                                                                                                                                      |
